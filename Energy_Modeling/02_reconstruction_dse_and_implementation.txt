12. THE FANOUT/REUSE TRADEOFF IS THE CENTRAL DSE
======================================================================

Treat reconstruction placement as a problem involving both temporal reuse
and spatial fanout.


12.1 AXIS 1: TEMPORAL REUSE

Question:
How many times is a reconstructed value consumed after reconstruction?

Low temporal reuse                         High temporal reuse
        |                                          |
        +------------------------------------------>
           Reconstruction cost becomes easier
           to amortize when the full result is retained

High temporal reuse favors:

Reconstruct once
      |
      v
Full decoded register
      |
      v
Reuse repeatedly

Relevant examples:
- Weight-stationary architectures.
- Simba.
- Portions of Eyeriss RS and RS+ execution.

Important distinction:
High reuse helps only when reconstruction is outside the repeated-use
loop or its result is retained. Reconstructing on every use does not gain
this amortization.


12.2 AXIS 2: SPATIAL FANOUT

Question:
How many PEs consume the same weight?

                   Source
                     |
                     v
               Reduced value
                     |
           +---------+---------+
           v         v         v
          PE        PE        PE

Two basic choices:


PRE-FANOUT RECONSTRUCTION

           Encoder
              |
              v
         Full 8-bit value
           /  |  \
          v   v   v
         PE  PE  PE

Characteristics:
- One encoder at this fanout source.
- One reconstruction can serve several consumers.
- Downstream multicast carries full-width values.


POST-FANOUT RECONSTRUCTION

        Reduced 4-bit value
           /  |  \
          /   |   \
         v    v    v
        XOR  XOR  XOR
         |    |    |
         v    v    v
        PE   PE   PE

Characteristics:
- Multiple destination encoders.
- Reduced-width network transport.
- Reconstruction may occur separately at each destination.
- Replicated area and leakage may matter.

This tradeoff requires an explicit experiment.

A hierarchical network also permits intermediate placement:
- Before global fanout.
- At destination-cluster boundaries.
- After local fanout.
- At individual PE inputs.

The DRAM interface sits above every fanout point, so its saving is the
same whichever of these is chosen.

13. EXAMPLE SHOWING WHY THE OPTIMUM MOVES
======================================================================

Illustrative representation:
- 8 total bits.
- 4 independent bits.
- 4 reconstructable bits.
- 64 uses of a weight.

This assumes independent reconstruction is feasible at the stated
granularity. See section 15 for group dependencies.

The DRAM interface carries 4 bits per weight under all three options and
is left out of the comparison below.


OPTION A: RECONSTRUCT BEFORE PE RF

NoC:             4-bit representation
Encoder:         1 reconstruction
RF storage:      8-bit weight
RF reads:        64 x 8-bit reads


OPTION B: RECONSTRUCT AFTER PE RF

NoC:             4-bit representation
RF storage:      4-bit representation
RF reads:        64 x 4-bit reads
Encoder:         64 reconstructions

Under the simplified read-and-encoder comparison, B beats A when:

64 * [E_RF(8) - E_RF(4)] > 63 * E_encoder

Interpretation:
- B saves RF read energy on 64 reads.
- B performs 63 additional reconstructions compared with A.

This equation omits differences in writes, capacity/leakage, controls,
timing, packing, and any other unequal costs. Include those in the full
model.


OPTION C: REDUCED RF PLUS DECODED REGISTER

NoC:                      4-bit representation
RF storage:               4-bit representation
RF reads:                 1 x 4-bit read
Encoder:                  1 reconstruction
Decoded-register reuse:   64 uses

Option C can potentially outperform both A and B.
    -- MEASURED 2026-09-10: IT DOES NOT. REMOVED. --
"Decoded-register reuse: 64 uses" assumes the same weight is used repeatedly
while resident. On the cached Timeloop mappings for resnet18 the number of
CONSECUTIVE MAC uses of one weight is 1 on 20 of the 21 layers, so a register
is reloaded on every access. Reuse need not be consecutive, but the register
must then hold the whole set the inner loops cycle through: 16-384 weights,
worst case 384, which is the entire pe_spad on simple_weight_stationary. A
register smaller than that set has a 0% hit rate (a cyclic walk is the worst
case for any replacement policy), so there is no useful middle size. See
01_project_context_and_architectures.txt Sec. 2.3.

Research implication (REVISED):
Reconstruction-result retention was carried through the DSE as boundary R4b and
is now removed from it. The best feasible boundary is the PE-local-memory INPUT
(R3), which needs no extra state and no mapping constraint.

IMPLEMENTATION CLARIFICATION:
A fair baseline may already retain a full weight in an operand register,
avoiding 64 RF reads. Compare equivalent reuse mechanisms. Do not attribute
ordinary register-reuse benefits entirely to ECC reconstruction.

For nonconsecutive reuse, a single register may be insufficient. Evaluate
the actual schedule and, if appropriate, a small cache with its lookup,
replacement, fill, storage, and energy costs.

14. EYERISS V2 ALREADY USES COMPRESSION
======================================================================

Eyeriss v2 processes sparse weights and activations using compressed CSC
representations, with separate weight address and data scratchpads.

ECC reduction therefore operates within an already compressed datapath.

Baseline representation:

CSC metadata
     +
Full weight-value bits

Proposed representation:

CSC metadata
     +
ECC-independent weight bits

Reducing weight values from 8 bits to 4 bits does not halve total storage
when entries also contain:
- Count bits.
- Address metadata.
- Column metadata.

Effective compression ratio:

C_effective =
    (Original value bits + Metadata bits)
    /
    (Reduced value bits + Metadata bits)

This expression assumes unchanged metadata. If the proposed organization
changes metadata or introduces group identifiers, include those costs.

Report value-bit reduction separately from complete representation
reduction.

Do not replace a 12-bit compressed entry with a 4-bit entry merely because
an 8-bit weight value was reduced to 4 bits; determine what every stored
field represents.

15. XOR RECONSTRUCTION MAY REQUIRE A COMPLETE ECC GROUP
======================================================================

The encoder may operate at codeword granularity rather than independent
weight granularity.

Illustrative parity relationships:

p0 = m0 XOR m1 XOR m4
p1 = m1 XOR m2 XOR m5

If these message bits belong to different weights, reconstructing one
weight can require retained bits from several weights.

The hardware may not support:

4 retained bits of Weight 1 --> Encoder --> Full Weight 1

It may instead require:

                 Retained bits W1
                        |
Retained bits W2 --------+------+
                        |      |
Retained bits W3 --------+------+
                        |      |
                        v      v
                      ECC encoder
                           |
                           v
                  Reconstructed group
                           |
                           v
                     W1 W2 W3 ...

Consequences:
- Group-assembly buffering.
- Encoder input width.
- Reconstruction latency.
- Packing and unpacking.
- Routing.
- Codeword alignment.
- Scheduling.
- Whether weights can be reconstructed independently.
- Whether all dependencies are available at a chosen boundary.

Define reconstruction granularity:

G_rec =
    Number of weights whose retained information must be available
    simultaneously to reconstruct an ECC group.

The exact dependency set can be more informative than a single scalar.

The same granularity applies at the DRAM side: the on-die decoder needs
the complete codeword, and the fetch must select the k message bits of a
codeword as a unit, not per weight.

Immediate implementation task:
Inspect the actual ECC generator relationships and weight-to-codeword
mapping before designing a PE-local encoder.

Determine:
- Which retained bits are needed for each reconstructed output bit?
- Which weights supply those bits?
- Whether the dependencies reach the same PE or cluster together.
- Whether sparse compression removes or reorders needed values.
- Whether group assembly requires additional transfers or storage.

Reconstruction granularity may be as important as XOR count.

16. WHAT SRAM READ/WRITE SAVING REALLY MEANS
======================================================================

Avoid unsupported claims such as:

"Reducing weights from 8 bits to 4 bits reduces SRAM energy by 50%."

A 64-bit SRAM access can still activate:
- Decoder.
- Wordline.
- Bitlines.
- Sense amplifiers.
- Peripheral circuitry.

Storing a representation such as:

xxxx0000 xxxx0000 ...

inside full-width words does not automatically halve physical energy.

Exploit the representation physically.


BASELINE PACKING

64-bit SRAM word
    =
8 full weights x 8 bits


REDUCED PACKING

64-bit SRAM word
    =
16 reduced weights x 4 bits

Now one access can return twice as many reduced weight representations.

Potential benefit:
Fewer physical accesses for the same number of useful weights.

Alternative:
A physically narrower memory organization, if supported by the chosen
memory implementation.

Model:
- Physical word width.
- Number of entries.
- Banking.
- Access granularity.
- Packing efficiency.
- Padding/alignment.
- Metadata.
- Packing/unpacking overhead.
- Group-assembly requirements.
- Number of useful values delivered per access.

At the DRAM the same rule is now SETTLED rather than assumed: the access is
custom-designed to collect the interleaved message bits, so the whole weight
term scales by k/n. See 01_..., Sec. 4.

Reduced logical bit count and reduced physical energy are related but are
not interchangeable.


WHO APPLIES THE SAVING -- ONE OWNER, DECLARED (2026-09-10)

The packing saving above can be applied in TWO places, and applying it in
both SQUARES it:

  the MAPPER     `datawidth: q` on the weight levels. Timeloop then counts
                 16 weights per 64-bit word instead of 8 and reports half the
                 accesses by itself. This is also what gives the mapper the
                 extra capacity, so for any mapping study it MUST be here.
  the EVALUATOR  a post-processing multiplier on the level's energy.

Rule: Timeloop owns an effect whenever Timeloop can express it; the evaluator
owns only what Timeloop cannot. The two sets are disjoint and the split is
DECLARED, not inferred from a mode name.

  on-chip storage width  -> mapper      (`datawidth: q`)
  DRAM x k/n             -> evaluator   (the array still holds all n bits;
                                         a 4-bit DRAM would also shrink the
                                         capacity the mapper thinks it has)
  network wire/switching -> evaluator   (the NoC level is datawidth 1 with an
                                         explicit word width; the mapper never
                                         sees the narrower operand)
  encoder, per access    -> mapper      (the ERT -- Sec. 19)
  encoder, per cycle     -> evaluator   (a price list cannot express it)

A check that asks "which packing MODE is selected" is not good enough: the
`aligned` mode is a no-op only when floor(W/q) == floor(W/8), which is true
for 7-bit values in a 24-bit word and FALSE for 4-bit values in a 64-bit one.
Measure the multiplier, do not read its name.

17. EXPERIMENTAL DSE VARIANTS
======================================================================

For each architecture, define applicable variants:

BASE
    Full representation throughout the modeled on-chip hierarchy. The
    complete codeword crosses the DRAM interface.

REC-L0
    Reconstruct at chip ingress (the weight input port). The DRAM
    interface carries k bits; nothing on chip is reduced.

REC-L1
    Reconstruct at global-buffer/input-buffer output.

REC-L2
    Reconstruct after the global NoC.

REC-L3
    Reconstruct at PE-local-memory input.

REC-L4
    Reconstruct at PE-local-memory output.

REC-L5  -- REMOVED 2026-09-10, see 01_..., Sec. 2.3 --
    Reconstruct at PE-local-memory output and retain reconstructed values
    in a decoded-weight reuse register/cache. Not implemented: there is no
    consecutive weight reuse to amortize over, and a register covering the
    cycled set is as large as the scratchpad it sits behind.

Every REC-L* variant carries k bits per codeword across the DRAM interface
and reads the complete codeword from the DRAM array.

Not every architecture contains every listed level. Mark nonexistent or
inapplicable boundaries explicitly instead of inventing them.

Sweep retained/full ratio:

k / n

Illustrative effective weight-width cases:
- 8 -> 7 bits.
- 8 -> 6 bits.
- 8 -> 5 bits.
- 8 -> 4 bits.
- 8 -> 3 bits.

Only evaluate reductions supported by the actual embedded-ECC scheme.
A numerical bit-width sweep does not prove a valid code or mapping exists
for every point.

Other central dimensions from the discussion:
- Temporal reuse.
- Spatial fanout.
- Reconstruction boundary.
- Reconstruction granularity.
- Encoder replication.
- Reconstructed-weight retention.
- Physical memory packing.
- Sparse metadata overhead.
- Per-bit DRAM cost, and the baseline's own higher one (Part 1, Sec. 4).

19. TIMELOOP + ACCELERGY FOR THE HIERARCHY MODEL
======================================================================

Timeloop models hierarchies of:
- Storage.
- Compute.
- Spatial organization.

Its statistics can expose accesses at storage and arithmetic levels.

The referenced Eyeriss example includes:

DRAM
shared_glb
ifmap_spad
weights_spad
psum_spad
MAC

It also specifies which tensors reside at or bypass each level.

Basic accounting:

Weight accesses at each hierarchy level
    x
Energy per physical access

Use reduced physical representations where appropriate.

The DRAM level needs two extra steps, both evaluator-side (Part 1, Sec. 4).
Accelergy's DRAM model is one flat per-bit constant and Timeloop charges the
DRAM-to-chip network zero, so:

  1. Replace the tool's per-bit constant with the cited one, and give the
     conventional baseline its own higher constant -- its array also holds
     the parity and it does the indexing the other arms do not.
  2. Scale the WHOLE DRAM weight term by k/n under every reconstruction
     boundary. No array/interface split is applied; the access collects the
     interleaved message bits, so the array reads fewer bits too.

Do not assume that changing a logical datawidth alone automatically models:
- Correct physical packing.
- Changed access counts.
- HM-NoC multicast behavior.
- CSC metadata.
- ECC-group dependencies.
- Reconstruction caching.
- Encoder throughput.
- Which side of the model owns a given saving.

Encoder integration options:
1. Add an explicit reconstruction component to Accelergy.
2. Post-process measured/derived reconstruction counts with characterized
   encoder costs.

WHICH OPTION IS RIGHT DEPENDS ON WHETHER THE MAPPER CAN MOVE THE COUNT
(2026-09-10). Option 2 is the default and it is what Task 3 does: the mapping
is fixed, every access count is Timeloop's, and the encoder cost is added
afterwards. It is also the ONLY defensible option for a boundary whose count
the mapping cannot change -- at the innermost boundary the count is the MAC
count, so the encoder term is a constant added to every mapping and putting it
in the objective cannot change which mapping wins.

Option 1 is what a boundary with a MAPPING-SENSITIVE count needs, and the
mechanism is the ERT rather than a new component: Timeloop's energy is
`sum over actions of count x ERT energy`, so adding the per-weight encoder
energy to the action whose count IS the reconstruction count puts the encoder
in the mapper's objective exactly. The action energy is per PHYSICAL access, so
the quantity added is

    E_encoder_per_weight x block_size,    block_size = width / datawidth

because Timeloop bills `vector_access_energy / block_size` per weight. The
encoder then costs `E_encoder_per_weight` per weight however the mapper tiles,
and the mapper trades fewer crossings of that boundary against whatever the
tiling costs elsewhere.

Note that Timeloop's own CONSTRAINTS mechanism is the wrong tool for this:
constraints prune the mapspace, they do not price it. A constraint is the right
mechanism only for FEASIBILITY -- the G_rec co-residency of section 15.

ONE CHARGING SITE PER ARM. Every weight crosses the encoder exactly once and
pays once. A boundary names ONE level and ONE action, and the bump goes there
and nowhere else. Charging both the buffer's read and the next level's write
looks like two halves of one transfer and is in fact the same toll collected
twice -- they describe two DIFFERENT chips, one encoder above the network and
one encoder per PE, which also differ by 168x in engine count. Pick the chip;
the cost follows.

WHICH ARM GETS ITS OWN MAPPING. Both must hold: the count is mapping-
sensitive, AND an ERT action exists whose count IS that count. On Eyeriss v1
that is the filter-GLB output and the PE scratchpad input. The chip-ingress
boundary moves only weakly, the column-edge boundary's count lives in the NoC
model rather than in a component action, and the spad-read boundary's count is
the MAC count, which no mapping can change.

ATTRIBUTION IS A SPLIT, NOT AN ADDITION. An ERT-injected arm already carries
the encoder energy inside the level's reported energy, and within one run
`accesses x E_per_weight` equals `events x incremental` exactly. So MOVE that
quantity out of the level's category into the reconstruction category; do not
add it. Compute it from THAT run's own access counts -- the whole point of the
exercise is that the counts changed.

Reconstruction energy, with the two denominators kept apart:

E_rec_total =
    incremental_per_codeword * N_reconstruct
  + idle_per_cycle * total_cycles * N_engines

Only the first term can go in the ERT; the second is per-cycle and the
evaluator owns it (Sec. 16). Use the same code configuration, width,
granularity, and operating conditions for the characterized encoder and the
architectural count.

A default "eyeriss-like" configuration is not automatically a faithful
Eyeriss-v2 implementation. Confirm topology, bypass rules, storage,
compression, and network behavior.

THE SYNTHESIS REPORTS TWO NUMBERS AND THEY HAVE DIFFERENT DENOMINATORS:

  incremental_per_codeword   energy burned performing one reconstruction
  idle_per_cycle             energy burned per clock while powered on

They may not be added. The first is charged per reconstruction event, the
second per cycle of the run per engine instance (Sec. 25, risk 6). Both are
tabulated per BCH configuration and both live in env.sh, not in Python.
Clocks must match between the two pipelines before either is used: the
synthesis clock period and the architectural cycle time are both 1 ns here,
so no rescaling is applied -- state it rather than assume it.

Use representative switching activity where available, and document:
- Technology/library.
- Voltage.
- Clock or throughput target.
- Encoder configuration.
- Input/output loading.
- Activity assumptions.
- Combinational versus pipelined organization.

SRAM modeling:

Do not synthesize a large array into flip-flops and report the result as
SRAM energy.

Appropriate sources can include:
- SRAM macro/library characterization.
- Memory compiler.
- CACTI.
- OpenRAM.
- Appropriate Accelergy SRAM models.

The source discussion emphasizes that Eyeriss-v2 weight storage includes
actual SRAM structures, not merely generic synthesized registers.

The on-die decoder is DRAM-process logic. If its energy is ever brought
into the comparison, characterize it for that process, not with the
accelerator's logic library.

Energy
  ^
  |  embedded, no reconstruction
  |- - - - - - - - - - - - - - - - - - - - - - - - -
  |\   <-- interface saving, every boundary
  | \

  |     \                      /
  |      \                    /

      Early                                  Late

Possible explanation:

Every boundary starts below the embedded reference by the DRAM-interface
saving. Moving reconstruction toward computation then saves:
- Upstream storage traffic.
- NoC traffic.
- Local-buffer traffic.

Extremely late reconstruction may repeatedly regenerate the same weight
for each MAC use.

change the argmax. R1's is the DRAM weight read count, which tiling moves only

ERT (section 19's "encoder integration option 1"), and R1, R3 and R5a stay
option 2, post-processed on the reference mapping. R3 has no ERT hook: its
count is a network delivery count, billed through the NoC model rather than
through a component action. prompt_6.md is the plan.

======================================================================
23. PROPOSED PAPER STORY
======================================================================

The contribution should be broader than:

"We reconstructed ECC bits with XOR gates near the PE."

Proposed framing:

Embedded ECC creates deterministically redundant weight bits. With the
decoder on the DRAM die and off the fetch path, those bits never need to
leave the die: only the message bits cross the DRAM interface, and they are
regenerated at a selected reconstruction boundary inside the accelerator.

Moving this boundary closer to computation can reduce storage and
communication costs, but can increase reconstruction multiplicity through
temporal reuse patterns and spatial fanout.

Conceptual DSE:

                   +----------------------+
                   | Reconstruction DSE   |
                   +-----------+----------+
                               |
           +-------------------+-------------------+
           v                   v                   v
    Storage hierarchy    Network fanout     Temporal reuse
    (from the DRAM             |                   |
     interface down)           |                   |
           +-------------------+-------------------+
                               |
                               v
                 Best reconstruction boundary
                 under measured constraints

Evaluate generality across:
1. Eyeriss v2 / RS+.
2. Weight stationary.
3. Eyeriss v1 / RS.
4. Output stationary.
5. Input stationary.
6. Simba.

Eyeriss v2 remains the initial and primary implementation target.

======================================================================
25. SIX MAIN RISKS TO THE STUDY
======================================================================

1. ECC DEPENDENCY GRANULARITY

Determine how many retained bits and weights must be simultaneously
available to reconstruct one group.

Do not assume every weight can be reconstructed independently.


2. PHYSICAL SRAM PACKING

Show that the reduced representation lowers physical accesses, memory
width, or another characterized physical cost.

Do not claim savings merely because unused bit positions contain zeros.


3. EYERISS-V2 CSC INTERACTION

Account for address/count/column metadata.

Do not equate value-bit reduction with total compressed-representation
reduction.

Check whether ECC grouping is compatible with sparse ordering and
zero-skipping.


4. FANOUT VERSUS RECONSTRUCTION MULTIPLICITY

Post-multicast reconstruction can save transport energy while replicating:
- Encoder instances.
- Reconstruction events.
- Area.
- Leakage.
- Potential buffering.

Measure the complete tradeoff.


5. TEMPORAL REUSE VERSUS RECONSTRUCTION MULTIPLICITY

Do not compare only encoder energy per reconstruction.

Also compare:

Encoder energy per useful MAC after amortization.

Count actual reconstructed-result reuse under the execution schedule.


6. THE ENCODER'S IDLE TERM AND ITS FANOUT
   (this slot used to hold "the DRAM array/interface split", which is
    SETTLED and removed -- see 01_..., Sec. 4)

The synthesised engine has a per-CODEWORD incremental energy and a per-CYCLE
idle energy. Adding them and multiplying by codeword count is dimensionally
wrong and was doing exactly that until 2026-09-10. Charge them separately,
and multiply the idle term by the number of ENGINES the placement needs.

That count is the risk. A boundary above the network needs one engine; a
boundary at the PE scratchpad input needs one per PE -- 168 on Eyeriss v1.
Measured on resnet18 layer3.0.conv1 (344,064 cycles), the idle term is
0.97 uJ at one engine and 163.6 uJ at 168, i.e. 0.2% of the run against 34%,
while the incremental term is under 0.4 uJ either way. The engine count,
not the mapping, is the dominant variable at any PE-local boundary.

Two consequences. Report engine count on every row. And note that no mapping
can remove a standby cost -- only a shorter run can -- so an idle-dominated
boundary is a LATENCY problem, not a data-movement one.

======================================================================
IMPLEMENTATION HANDOFF NOTES
======================================================================

These notes make the implications of the discussion explicit; they are
not claims that an implementation already exists.

Before making architectural changes:

1. Inspect the repository and its existing Timeloop/Accelergy flow.
2. Identify the actual baseline architecture configuration.
3. Inspect the ECC parameters, generator relationships, and weight mapping.
4. Establish reconstruction granularity and dependency availability.
5. Scale the WHOLE DRAM weight term by k/n (the access collects only the
   interleaved message bits; there is no array/interface split), and price
   the conventional baseline's larger, indexed array per BIT rather than as
   extra traffic.
6. Define physically packed reduced representations, including metadata.
7. Implement the initial Eyeriss-v2 variants.
8. Derive reconstruction counts from actual events and reuse schedules.
9. Characterize the corresponding encoder implementation.
10. Combine costs without double-counting.
11. Compare energy, area, and latency against an equivalent baseline.

Do not assume:
- A default Eyeriss-like model is Eyeriss v2.
- Weights reside in a global buffer in every architecture.
- Half the value bits means half the SRAM or NoC energy.
- The conventional baseline moves more DRAM traffic than the embedded arm.
  (It does not: its parity is corrected on the die. It pays a dearer BIT.)
- Two parts of the model may each apply the same saving. Exactly one owns it.
- Every weight can be reconstructed independently.
- A single latch captures all reuse.   <-- MEASURED FALSE 2026-09-10; removed.
- Late reconstruction always wins.
- An added encoder is free in timing, area, leakage, or control.
- The qualitative ratings are experimental results.

The deliverable is a reproducible, configurable evaluation that can
determine the best reconstruction boundary, not an implementation designed
to confirm a predetermined winner.
