PROJECT CONTEXT: ECC WEIGHT RECONSTRUCTION IN AI ACCELERATOR DATAPATHS
PART 1: PROJECT FOUNDATIONS AND ARCHITECTURES — SECTIONS 1–11

Source conversation:
https://chatgpt.com/share/6a9cf72e-979c-83e9-932b-c6193b111007

Revised 2026-09-09: the ECC decoder moves onto the DRAM die and off the
fetch path, so the reduced representation starts at the DRAM interface
instead of at an on-chip ECC engine. Every diagram and table below is
written against that model. Section 1 defines it; nothing else is new.

PURPOSE OF THIS FILE

This file provides project context for an LLM coding assistant implementing
an architectural design-space exploration of ECC-derived weight
reconstruction in AI accelerators.

The primary target is Eyeriss v2. The methodology should also support:
- Eyeriss v1.
- Generic weight-stationary (WS) architectures.
- Generic output-stationary (OS) architectures.
- Generic input-stationary (IS) architectures.
- Simba.

The central idea is to let only the independent (message) portion of an
embedded-ECC weight representation leave the DRAM die, carry that reduced
form through selected parts of the on-chip hierarchy, and reconstruct the
omitted dependent bits with XOR encoders before computation.

Example:
- Original embedded weight representation: 8 bits.
- Retained information: approximately 3–4 bits per weight.
- Remaining bits: deterministically reconstructed from ECC relationships.

IMPORTANT:
The per-weight example is illustrative. Actual ECC dependencies span
multiple weights in a codeword. Part 2, section 15 explains this constraint.
Do not implement an independent per-weight encoder unless the ECC mapping
actually supports it.

The research question is not simply where XOR gates can be inserted. It is
where the reduced representation should stop and the full representation
should resume to minimize total cost while meeting throughput, timing,
capacity, and reliability requirements.

Three central quantities:
1. How many bits can remain omitted up to a candidate boundary?
2. How much temporal reuse occurs after reconstruction?
3. How much spatial fanout occurs before or after reconstruction?

Working framing:
"Reconstruction-boundary optimization from the DRAM interface across the
accelerator memory/interconnect hierarchy."

1. CORRECT CONCEPTUAL MODEL FOR THE ECC SCHEME
======================================================================

An oversimplified view is:

DRAM --> SRAM --> RF --> PE
          ^
       Encoder?

A decoder on the fetch path forces the complete n-bit codeword across the
DRAM interface on every fetch. The model used here puts the decoder ON THE
DRAM DIE and OFF the fetch path:

                          DRAM DIE  (reliability domain)
+----------------------------------------------------------------+
| DRAM array: complete embedded-ECC codeword (n bits)            |
|          |                                                     |
|          v                                                     |
| On-die ECC decode / correction                                 |
|   runs at write, on a scrub pass, or on a prior access --      |
|   NOT on the fetch path                                        |
|          |                                                     |
|          v                                                     |
| Fetch: drive only the k message bits off the die;              |
|        the n-k parity positions never leave it                 |
+----------+-----------------------------------------------------+
           |
           |  DRAM INTERFACE (I/O, link, controller-to-accelerator port)
           |  carries k of every n bits  <-- the first saving, shared by
           |                                 EVERY reconstruction boundary
           v
       Reduced representation on chip
       Example: 4 retained bits instead of 8 full bits
           |
           |    ON-CHIP RECONSTRUCTION DOMAIN
           |
           +-------------- R1  (chip ingress)
           v
       Global storage
           |
           +-------------- R2
           v
          NoC
           |
           +-------------- R3
           v
       Local weight storage
           |
           +-------------- R4
           v
      Weight register/latch
           |
           +-------------- R5
           v
          MAC

Research question:

How deep into the accelerator can the reduced representation be propagated
before the cost of repeated reconstruction becomes larger than the
additional storage and communication energy saved? The DRAM-interface
saving is common to every boundary; the boundaries differ on chip.

Reliability constraint:

The reconstructable bits must not be discarded before ECC correction. With
an on-die decoder that constraint is met on the die: the array keeps and
reads the complete codeword, correction happens before any fetch, and the
discard happens at the die's output.

Required conceptual sequence:

Array holds full codeword --> on-die correction (off the fetch path)
    --> fetch selects k message bits --> interface carries k bits
    --> accelerator reduced-representation datapath

What IS credited at the DRAM:
- DRAM interface energy scales by k/n under every reconstruction boundary.

What is NOT credited at the DRAM:
- DRAM array energy. The array stores and, for correction, reads the
  complete codeword. Whether a message-only fetch touches fewer array bits
  depends on burst granularity and the codeword layout; do not assume it.
- Decoder energy. The decoder is the same BCH decoder relocated to the
  DRAM die; it runs once per corrected codeword and sits outside the
  placement comparison. Record that it is DRAM-process logic.

Reference bars are unchanged: the conventional baseline is side-band ECC,
so its external parity is read from the array AND crosses the interface;
the embedded arm without reconstruction consumes every weight bit on chip,
so its complete codeword crosses the interface too.

Reconstructing at an SRAM input restores full-width data before storage,
so that SRAM does not receive the reduced-storage benefit. Upstream
transport, starting with the DRAM interface, still benefits.

2.3 LATE RECONSTRUCTION WITH A RECONSTRUCTED-WEIGHT LATCH/CACHE
    -- REJECTED AND REMOVED FROM THE STUDY, 2026-09-10 --

The proposal was to hold reconstructed weights in a register/latch between the
weight SPad and the MAC, so one reconstruction could serve many MAC uses:

    4-bit SPad --> XOR encoder --> reconstructed-weight register --> MAC
                                            +--> reuse x N

It was rated 5/5 on architectural promise and evaluated as boundary R4b. IT DOES
NOT WORK, and the measurement is not close:

  * A LATCH CATCHES NOTHING. Measured on the cached Timeloop mappings for
    resnet18, the number of MAC operations that use the same weight
    CONSECUTIVELY is 1 on 20 of the 21 layers (the exception is conv1, at 196).
    The innermost temporal loops below the scratchpad walk weight dimensions
    (C, R, S), so the required weight changes every cycle and a 1-, 2- or
    4-entry register is reloaded on every access.
  * A REGISTER THAT DOES PAY IS A SECOND SCRATCHPAD. Reuse does not need to be
    consecutive, but the register must then hold the whole set the inner loops
    cycle through. That set is 16-384 weights across the layers, worst case 384
    -- and simple_weight_stationary's pe_spad holds exactly 384 weights. There
    is no useful middle: a register smaller than the cycled set has a 0% hit
    rate, because a cyclic walk is the worst case for any replacement policy.
  * NO DATAFLOW IN THE STUDY ESCAPES THIS. Weight-stationary is the best case
    and already fails. Output- and input-stationary hold the psum or the
    activation in the PE by definition, so weights stream past the MAC faster
    still. Simba's PE behaves like Eyeriss v2, where the boundary is infeasible
    anyway (fewer than G_rec = 9 weights resident in 4 of 21 layers).
  * THE MAPPER CANNOT BE ASKED TO FIX IT CHEAPLY. Holding a weight while
    sweeping output positions is expressible as a loop-order constraint, and
    Timeloop does produce such a nest for conv1 (P14/Q14 innermost). But weight
    reuse trades directly against psum residency -- 196 consecutive uses needs
    196 partial sums live in the PE -- so buying it costs more in psum traffic
    than the boundary was worth. R4b beat R3 by only 1.34 points even with a
    384-entry register charged nothing for area or leakage.

CONCLUSION: reconstruct at the PE weight-SPad INPUT (R3). It needs no extra
state, no mapping constraint, and it is the lowest-energy feasible boundary on
both designs measured. Every R4b row, rating and diagram below is retained only
as a record of the rejected option; the code no longer implements it.


======================================================================
3. RATING SYSTEM
======================================================================

The source discussion used architectural promise ratings, not experimental
results.

| Rating | Interpretation |
|--------|----------------|
| 5/5 | Extremely promising reconstruction boundary |
| 4/5 | Strong candidate worth evaluating |
| 3/5 | Useful tradeoff point |
| 2/5 | Usually less attractive than another placement |
| 1/5 | Generally not worthwhile |

All ratings assume the reduced representation is physically exploited:
- Packed weights.
- Fewer accesses.
- Narrower transfers.
- Appropriate memory organization.

The DRAM-interface saving is the same for every boundary of one
architecture, so it does not change the relative ratings. It changes the
absolute saving of every boundary, including the earliest.

Merely leaving unused bits in a full-width word does not establish
proportional energy savings.

4. ENERGY MODEL
======================================================================

For reconstruction placement r, define:

n:
    Full representation width.

k:
    Retained representation width, where k < n.

A_l:
    Number of accesses/transfers at hierarchy level l.

E_l(b):
    Energy of accessing/transferring b bits at hierarchy level l.

N_rec(r):
    Number of reconstructions at placement r.

E_rec:
    Energy per reconstruction.

E_control(r):
    Additional control energy associated with placement r.

DRAM term. A DRAM read has two physical parts, and only one of them gets
smaller when fewer bits leave the die:

E_array      reading the complete n-bit codeword out of the array. A row
             activation and a burst move whole words; they cannot pick the
             k message bits out of a chunk. Never reduced.
E_interface  driving bits off the die: I/O drivers, link, controller port.
             Proportional to the bits sent, so reduced to k of n.

E_DRAM(embedded, no reconstruction) = E_array + E_interface
E_DRAM(r), every boundary           = E_array + E_interface * k/n

The modeling tool bills DRAM as ONE per-bit number that contains both
parts, so the evaluator needs the interface share of that number:

f_if = E_interface / (E_array + E_interface)

f_if is the only new parameter. It comes from a cited DRAM energy breakdown,
not from code; when it is uncertain, print the DRAM saving at several values.
f_if = 0 would mean no DRAM saving at all; f_if = 1 would claim the array
also reads fewer bits, which needs physical justification.

Conceptual model:

E(r) =
    E_DRAM(r)
  + SUM over l in partial(r) [A_l * E_l(k)]
  + SUM over l in full(r)    [A_l * E_l(n)]
  + N_rec(r) * E_rec
  + E_control(r)

Boundary interpretation:

DRAM interface | Reduced representation | Full representation
               |                        ^
        always reduced             Reconstruction

Moving the boundary toward computation can save more data movement, but
may increase N_rec.

Implementation interpretation:
This is a conceptual accounting model. If packing or remapping changes
physical access counts, use placement-dependent physical counts rather
than assuming A_l remains identical for every variant.

The complete evaluation must also account for relevant leakage, buffering,
packing/unpacking, and timing overheads.

Use a consistent granularity for n, k, and E_rec:
- Per weight, only if reconstruction is independent per weight.
- Per ECC group/codeword, if dependencies span multiple weights.

5.1 ACTUAL HIERARCHY

Eyeriss v2 uses:
- Row-stationary-plus (RS+) dataflow.
- A hierarchical-mesh network on chip (HM-NoC).
- PE clusters.
- Router clusters.
- Global-buffer clusters.
- Separate networks for different data types.
- Communication modes supporting different reuse patterns.

The source discussion describes published PE-local CSC weight storage as:
- Weight-data scratchpad: 96 x 24 bits.
- Weight-address scratchpad: 16 x 7 bits.
- Capacity corresponding to up to 192 12-bit compressed weight entries.

These implementation-specific quantities should be verified before
hard-coding them into the model.

The original Eyeriss-v2 GLB should not automatically be modeled as a
conventional large global weight SRAM. The source discussion states that
its GLB SRAM banks serve input activations and partial sums, with dedicated

Illustrative example: one weight participates in 100 MACs.

Reconstruction before RF:
- 1 reconstruction.
- 100 full-width RF reads, under this illustrative access model.

Reduced RF plus reconstruction on every read:
- 100 reduced-width RF reads.
- 100 reconstructions.

Reduced RF plus stationary decoded register:
- 1 reduced RF read.
- 1 reconstruction.
- 100 register reuses.

These counts describe alternative access organizations, not a universal
property of all WS hardware. A fair baseline should include any stationary
register and reuse mechanism already present.

8. OUTPUT-STATIONARY
======================================================================

In output-stationary dataflow, partial sums remain local while weights and
activations are supplied to the PE.

Weights ----> PE: partial sum remains here
Inputs  ----> PE

Canonical hierarchy:

DRAM array (on-die ECC)
  |
  v
DRAM interface: k bits per codeword
  |
  v
Weight buffer / global SRAM
  |
  v
NoC / systolic injection
  |
  v
PE
  |
  +--> Streamed weight
  +--> Streamed activation
  +--> Stationary partial-sum RF
  |
  v
Output

Weights are streaming operands in this abstraction.

Reconstructing much earlier than the PE expands the weight representation
while it is still being transported.

8.2 OUTPUT-STATIONARY TABLE

| Level | Function | Weight behavior | Reconstruction | Advantages | Disadvantages | Rating |
|-------|----------|-----------------|----------------|------------|---------------|--------|
| DRAM array | Full embedded-ECC storage; on-die correction off the fetch path | Stored | No | Complete protection | Complete codeword read; no array saving | N/A |
| DRAM interface / controller | Carries k message bits per codeword | Full to reduced | Strip on the die | Interface energy x k/n, every boundary | On-die decoder logic | Essential |
| Weight SRAM/GLB | Buffers weights | Reduced | Output | SRAM saving | Expands before NoC | 3/5 |
| Weight NoC | Delivers weights | Reduced | Destination | Reduced bandwidth/switching | Encoder duplication may be needed | 5/5 |
| PE input FIFO | Buffers incoming weights | Reduced | FIFO output | Narrow local FIFO | Reconstruction per delivered weight/group | 4/5 |
| MAC operand latch | Holds short-lived operand | Full | Latch input | Very late reconstruction | Must sustain operand demand | REMOVED 2026-09-10 (Sec. 2.3); the MAC-input boundary itself is retained and reported INFEASIBLE (G_rec = 9) |
| Partial-sum RF | Stores outputs | Not weight storage | No | N/A | N/A | N/A |

Promising path:

DRAM (on-die ECC) --4 bits--> NoC ----> PE --> XOR --> MAC

Earlier alternative:

DRAM (on-die ECC) --4 bits--> XOR --> 8-bit weight ---- NoC ----> PE

The earlier alternative keeps the interface saving but sacrifices
reduced-width NoC traffic.

High multicast fanout can change the result:

Option 1:
1 encoder + full-width multicast to 100 PEs.

Option 2:
100 destination encoders + reduced-width multicast.

Evaluate both rather than assuming late reconstruction always wins.

9. INPUT-STATIONARY
======================================================================

Input-stationary dataflow retains activations locally while weights are
supplied to the array.

             Stationary activation
                     |
                     v
Weights -----------> PE -----------> Partial sum
Weights -----------> PE -----------> Partial sum
Weights -----------> PE -----------> Partial sum

For weight reconstruction, IS resembles the streaming-weight OS
abstraction. The difference is which other operand receives stationary
reuse.

10. SIMBA
======================================================================

Simba provides a multi-level weight-stationary architecture.

Hierarchy:

Package
   |
   v
Chiplet
   |
   v
PE

Communication:
- Network on package (NoP) between chiplets.
- Network on chip (NoC) within a chiplet.

The source discussion describes each PE as containing:
- Distributed weight buffer.
- Input buffer.
- Parallel vector-MAC units.
- Accumulation buffer.
- Post-processing hardware.

Key feature:
Weights remain in vector-MAC registers and are reused while new inputs
are supplied each cycle.

11. CROSS-ARCHITECTURE COMPARISON
======================================================================

These rankings are hypotheses. The DRAM-interface saving is common to every
column of one row, so it moves every boundary of an architecture by the
same amount and does not reorder the columns.

The "decoded reuse register" column is REMOVED (2026-09-10, Sec. 2.3): the
register it assumes has to hold the whole set the inner loops cycle through
(16-384 weights, worst case the entire scratchpad), because consecutive weight
reuse is 1 on 20 of 21 resnet18 layers. It is struck through below rather than
deleted so the rejected hypothesis stays on the record.

| Architecture | Early/global reconstruction | After NoC | Local weight-storage output | ~~Local output + decoded reuse register~~ | Likely best candidate |
|--------------|-----------------------------|-----------|-----------------------------|---------------------------------------|-----------------------|
| Eyeriss v2 | 2/5 | 4/5 | 3/5 | ~~5/5~~ REMOVED | SPad INPUT (R3) |
| Weight stationary | 3/5 | 4/5 | 2/5 for naive repeated encoding | ~~5/5~~ REMOVED | PE INPUT (R3) |
| Eyeriss v1 | 3/5 | 4/5 | 3/5 | ~~5/5~~ REMOVED | SPad INPUT (R3) |
| Output stationary | 3/5 | 5/5 | 4/5 | n/a -- holds the psum, not the weight | Destination-side NoC/PE input |
| Input stationary | 3/5 | 5/5 | 4/5 | n/a -- holds the activation, not the weight | Destination-side NoC/PE input |
| Simba | 2/5 | 4/5 | 5/5 | ~~5/5~~ REMOVED | Distributed weight-buffer output |

MEASURED OUTCOME (2026-09-10): the best feasible boundary is the PE weight-SPad
INPUT (R3) on both designs evaluated -- +11.07% vs embedded on
simple_weight_stationary and +17.24% on eyeriss_like. It needs no extra state
and no mapping constraint.

General hypothesis, as originally written and now FALSIFIED:

Architectures with strong local weight reuse favor reconstruction
immediately before a small stationary decoded-weight register.
  -> The premise fails: the mappings these designs actually choose walk weight
     dimensions in the innermost temporal loops, so there is no local weight
     reuse for a small register to exploit.

Architectures with streaming weights favor reconstruction after the
weight-distribution network, subject to fanout, forwarding, and encoder
throughput costs.

Architectures whose weight energy is dominated by DRAM refetch gain most
from the interface term, which every boundary receives.

Do not hard-code these rankings as the outcome of the DSE.
The implementation must measure the relevant counts and costs.
