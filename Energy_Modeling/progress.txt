2026-09-13  RESTRUCTURE PHASE 5 -- A DESIGN IS A DIRECTORY
-----------------------------------------------------------------------

ADDING AN ARCHITECTURE WAS 14 EDITS ACROSS 6 FILES IN 3 LANGUAGES. It is now one
directory:

    archs/<name>/ arch_paper.yaml  design.yaml  weight_path.yaml
                  placements.yaml  README.md

`make arch NEW=<name>` writes it. Nothing else in the project is edited, and
`tests/contract/test_designs_are_data.py` holds that at zero: it walks the AST of
every production module and fails on a comparison against a design NAME.

WHAT MOVED OUT OF PYTHON:
  * WEIGHT_PATHS and PLACEMENTS (five tuples and four, ~900 lines of cited
    prose) -> weight_path.yaml + placements.yaml per design. Every string moved
    byte for byte; the emitter is restructure/emit_design_data.py.
  * KNOWN_ARCHS, ARCH_LABELS, BRACKET_PAIRS -> design.yaml, read by
    arch/design.py. `config.KNOWN_ARCHS` still answers, and is now a function of
    the directory.
  * MAPSPACE_FREE_LEVELS (prompt_3's constrained search) -> design.yaml.
  * THE THREE `arch.startswith("eyeriss_v2")` BRANCHES -> two declared fields.
    `weights_stored_compressed` carries the CSC caveat onto every result;
    `noc_published_share` (with its citation, and REFUSED without one) is the
    band audit/baseline check the modelled share against. The check KEY keeps
    the design in its name on purpose -- it identifies a check in every result
    file already written.

THE TWO HALVES ARE ONE DIRECTORY, which is what makes "the two tables must be
edited together" structural instead of a warning in CLAUDE.md. A design declares
both files or neither: three designs (simba_like, simple_input_stationary,
simple_output_stationary) declare no boundaries and the schema says so rather
than inventing a weight path that was never cited.

THE SCHEMA IS A REFUSAL AND IT NAMES THE FILE: a stage of an unknown kind, a
boundary naming a stage that does not exist, a `noc_published_share` with no
citation, and -- the one that makes the scaffold safe -- a `TODO` left in an
`evidence:` or a `description:`. A stub that VALIDATED would be a design whose
weight path nobody wrote, and the placement study would report savings against
it. Proven by running `make arch` and watching the load refuse.

WHAT IS NOT CHECKED AT LOAD, ON PURPOSE: the prefix rule and the reachability
rule. `arch.arms.validate_placement_space()` states both over the stages a
CONFIGURATION resolves (ECC_RECON_DECODE_SITE=controller makes the DRAM stage
irreducible), and checking the declared file instead would refuse
`eyeriss_v2_like_wglb` AT IMPORT -- its weight_glb stage is reducible and no
boundary reaches it, a known documented gap. It is refused when the study asks
for it, with the reason, and does not stop every other design from loading.

TWO THINGS THE DIRECTORY DOES NOT OWN. The design's CLOCK stays in env.sh
section 7 (a knob a run may override; one file a user edits). And `order:` --
where a design sits on a default axis -- is optional and declared, because
KNOWN_ARCHS is the default value of ECC_SWEEP_ARCHS and the resolved arch list
is in the mapper fingerprint: an alphabetical directory listing would have
silently reordered it.

ONE BEHAVIOUR PRESERVED DELIBERATELY: ECC_SWEEP_ARCHS UNSET means "every
declared design" and is filled in by config._resolve(); ECC_SWEEP_ARCHS=" " is
still REFUSED. A plain default could not tell those apart once the design list
stopped living at L0, so `settings/env.py` grew `_list_or_none()`.

2026-09-13  RESTRUCTURE PHASE 4 -- THE KNOBS FROZEN, AND THE CYCLE IS DEAD
-----------------------------------------------------------------------
ProjectRestructure.md section 9.2, phase 4. Gate: 302 fingerprints
BYTE-IDENTICAL, every evaluated total identical to the pJ, 231 -> 240 passing
(+8 contract tests, and the layer-rule xfail is a plain pass now).

`Config`'s 112 fields became SIX FROZEN dataclasses in eccenergy/settings/ --
run, code, arch, mapper, recon, energy -- each owning its own ECC_* knobs, its
own registry of legal values, and its own IN_FINGERPRINT declaration. env.py is
the only reader of os.environ; banner.py prints. The package imports nothing but
contracts/ and paths/.

THE CYCLE DIED BY MOVING config.py UP, NOT BY HIDING THE IMPORT. The knobs are
L0; RESOLVING them is a different job -- the ERT arm has to exist on THIS chip,
the axis lists have to name real models, code_t comes out of the BCH table --
and it needs arch/ and physics/. So config.py now sits ABOVE arch/ at L3, its
six lazy imports are plain top-level ones, and nothing at or below arch/ imports
it. tests/contract/test_layer_rule.py's exception list went 16 -> 8 -> ZERO.

The last two exceptions were not config's: arch/fingerprint.py and arch/arms.py
priced an ERT bump from `study.stacks.load_recon_energy`, reaching up into a
driver. The DC table lookup moved to physics/recon_dc.py -- the one module in
physics/ that reads a file, declared in the package docstring, because
data/dc/BCH_N63_results.json is a cited static MEASUREMENT and not a cache.

WHAT IS PRESERVED, AND HOW IT WAS CHECKED. Two properties of Config are BYTES ON
DISK, and a refactor can move either without moving a number:
  * to_dict()'s KEY ORDER -- every manifest and every result carries it, written
    with indent=1 and no sort_keys. FIELD_ORDER pins it; the live dict was
    captured before the split and compared key for key and value for value.
  * fingerprint()'s HASHED SET -- now assembled from the six groups' own
    declarations instead of one hand-kept list. json.dumps(sort_keys=True) makes
    it an unordered SET, which is what lets it be assembled from six pieces and
    still hash byte-identically. tests/contract/test_settings.py pins it against
    the pre-phase-4 `keep` tuple, verbatim, with the cost of a miss in the
    message.

`dataclasses.replace(cfg, ...)` IS GONE and had to be: replacing one field of a
six-part object leaves the other five derived from the old value. `cfg.with_()`
routes a knob by name to the group that owns it and re-runs _resolve(), which is
__post_init__ moved out whole -- same checks, same order, same messages, because
each of them is a finding somebody paid for. 84 call sites converted
mechanically (an AST rewrite that only fires when every keyword is a known
knob, so the ~20 replace() calls on Placement and Stage were left alone), 8 more
by hand where the keywords were **kwargs.

ONE VALIDATOR, NOT SIX, on purpose: the rules are about a WHOLE configuration --
the sweep against the code, the experiment against the phase, the arm against
the design -- and six partial validators would each see a third of the picture.

WHAT PHASE 4 DID NOT DO. Section 9.2 also says "update every signature to take
what it needs". Not done: `cfg.victory` and `cfg.mapper.victory` are both
available and every call site still says the first. The groups exist now, so
that conversion is incremental and can ride along with phase 7 instead of being
one 1,000-site diff that no gate can attribute.

2026-09-12  PROMPT_7 PHASE B -- SIX CHIPS, AND R3 WAS ON THE WRONG PLAN
-----------------------------------------------------------------------
Defect 3. No mapper run, no cache colded, no job submitted.

recon.mapper_arms(arch, cfg) is new and answers the question the launcher
actually has: WHICH BOUNDARIES ARE A DISTINCT CHIP. Derived from prompt_7
section 6.4's three axes -- datawidth: q on the storage levels the boundary
narrows, the ERT bump, the declared per-dataspace bandwidth scale. Six on
eyeriss_like_wglb, five on eyeriss_v2_like (four boundaries). A NETWORK stage
is carried in the bandwidth-scale set and MARKED no-op rather than dropped:
Timeloop has no network timing model to apply it to, but a boundary that adds
one is still a different declaration, and dropping those entries collapses
v2's R1 and R2 into one chip. recon.ert_arms() keeps its older, narrower
meaning -- which boundaries have an ERT-injectable encoder -- and is now a
strict subset of the arm list.

R3 STOPS BORROWING THE REFERENCE'S PLAN. recon.plan_assignment() derives, per
bar: its own arm if that arm is mapped; else the OUTERMOST mapped arm in path
order that narrows exactly the same storage levels; else the reference, FLAGGED
geometry_matches: false. With only the two prompt_6 arms on disk that is
R1 -> reference (right, not a fallback: R1 narrows nothing on chip),
R3 -> R2, R5a -> reference and flagged as section 6.2b's chip that has never
been mapped. Every bar carries billed_from on its record and the figure prints
the plan under the bar. A HALF-mapped arm is refused rather than borrowed (two
chips in one bar); ECC_RECON_ERT_AWARE=1 with no arm mapped at all is refused
as Task 3 under a heading that says otherwise.

MEASURED EFFECT (mobilenet_v2, BCH(63,39), gating 99.5): R3 6,376.502 ->
6,232.748 uJ, +11.11 % -> +13.11 % vs conventional ECC, +3.58 % -> +5.75 % vs
embedded. Its RULE 1 narrowing owner moved from the evaluator (x0.6316) to the
mapper (x1.0000), which is the mechanism: on R2's plan filter_glb's Word bits
is 5. Its reconstruction term fell 9.094 -> 7.718 uJ on 1,688,225 events
instead of 2,012,784. NO OTHER BAR MOVED.

CONDITION 3 RE-DERIVED (section 6.3). The ERT bump has two rows and the
exclusion needs both constant. The access row on the innermost level's reads is
the MAC count and is; the per-cycle leak row is idle x (1 - g), which Timeloop
bills as leak x UTILIZED instances x cycles. From the live DC constants:
2.7891299 pJ/cycle/instance at PCT=0, 0.0139456 at 99.5, exactly 0 at 100. So
R5a IS ERT-injectable at both settings section 11 item 7 requires side by side,
and is not at the fully-gated limit. Renaming the placement moves nothing.

ONE REAL COLLISION, NOT A THEORETICAL ONE. R1's patched YAML IS the reference's
until Phase C1.2 declares the bandwidth scale, so with no ERT bump and no
narrowed level it produced the reference's cache slug exactly. Arms without a
bump now get `arm-<key>`; arms with one keep prompt_6's
`ert-<key>-<level>-<action>` byte for byte, which is why nothing on disk moved.

SOMETHING PHASE A'S TABLE COULD NOT SHOW. Once the bars stop sharing one plan,
a bar can pass the latency ceiling -- which is computed on the REFERENCE plan's
off-chip traffic and bounds the WEIGHT term only. R2/R3/R4 reach 5.84 % against
a 4.32 % ceiling at IDENTICAL weight reads (x1.000) and x0.983 activation items
(30,508,939 against 31,042,059). The 1.52 pp is the arm's own loop nest moving
less activation traffic off chip: a MAPPING effect, not a reconstruction one.
Those plans are also SLOWER by Timeloop's own count (3,937,072 vs 3,855,536) and
faster under the 480 MB/s roofline, which is what a DRAM-bound machine looks
like. The table now prints wt and act per bar and a recorded check refuses a bar

2026-09-13  GROUP RESIDENCY: REPORTED, NOT REFUSED (the user's decision)
--------------------------------------------------------------------------------
After Phase C2 the mobilenet_v2 figure carried R1 and nothing else: R2-R5a came
back `unsupported`, with the reason "infeasible local placement: N (layer,
stage) pair(s) keep fewer than G_rec = 9 weights resident".

WHAT G_rec IS. The embedded layout is ONE BIT STREAM cut into 63-bit codewords.
63/8 = 7.875 is not a whole number, so codewords drift across weight boundaries
and the worst-aligned one reaches into ceil(63/8)+1 = 9 weights. G_rec is that
9: the weights whose retained bits a single codeword touches.

WHAT CHANGED, AND IT WAS REAL. Under the declared off-chip limit the
EDP-optimal plan for ONE layer shrank its weight tile:

    features.1.conv.0.0   filter_glb resident weights:  12 -> 6     (G_rec 9)

Every other depthwise shape stayed at or above 9; most went UP. resnet18 has no
layer below G_rec at all, which is why it kept all five bars. R2/R3 failed on 1
layer of 31, R4 on 4, R5a on 14 -- and R5a had ALREADY been `unsupported`
before Phase C, so only R2/R3/R4 were new.

THE DECISION (the user's, and it is about their hardware, not about Timeloop).
The refusal assumed an engine that can only rebuild from weights co-resident in
the level AT ONE INSTANT. RECAP's reconstruction engine does not work that way:
it accumulates the retained bits as they arrive and rebuilds when the group
completes, so a level holding 6 -- or 1 -- still feeds it, over more accesses
and with more buffering. A small resident tile is therefore a COST, not an
impossibility, and deleting the bar overstated what the hardware cannot do.

WHAT LANDED. `ECC_RECON_REQUIRE_GROUP_RESIDENCY` (env.sh section 4, default 0).
At 0 the shortfall is MEASURED and REPORTED and the bar is charged; at 1 the old
refusal comes back for an engine with no group buffer. The number is not lost --
every bar's record carries `layers_below_G_rec`, `infeasible_layers` with the
per-layer resident counts, and a `group_residency_note` naming the layers and
the fewest weights any of them holds, because THAT NUMBER BOUNDS THE BUFFER the
engine needs. Same rule PE-count differences already follow: report, do not
refuse. test_a_pe_local_boundary_is_rejected_when_the_tile_is_smaller_than_g_rec
now asserts BOTH readings, and its breakage is a shortfall that is neither
refused nor recorded -- the one outcome neither reading allows.

                = (n - 8*floor(k/8)) / (8*floor(k/8))        -- k cancels

THE SHAPE OF IT
--------------------------------------------------------------------------
A CHIP is (architecture, code K, buffer-depth scale, arm) -- every distinct
thing the mapper is handed, with its own arch_fingerprint() and its own cache
directory. A UNIT is one chip x one distinct layer SHAPE: one Timeloop search,
one cache entry. The three launchers existed only because they enumerated
chips along different axes; there is one enumerator now.

  eccenergy/toolchain/units.py   NEW (L4). enumerate_units(cfg) -> every unit
      the configuration needs, each marked cached or cold; bundle() assigns
      the SLURM array indices. `--tasks` prints the task file, `--tasks --all`
      includes cached units (the smoke test), bare prints the BILL.
      THE ARMS ARE DERIVED (arch.arms.mapper_arms: the reference plus every
      boundary that differs on datawidth q x the ERT bump x the declared
      bandwidth scale), filtered by ECC_APPROACHES. THE SHAPES come out of the
      workload file, one representative layer per distinct shape. CACHED is
      `Mapper._accept_cached`'s own answer -- stats.txt AND a mapping.json
      sidecar whose fingerprint, ERT bump and MAC price match -- never a file
      count, so a mapping of another geometry is never read as a hit.

  hpc/.runtime/tasks.txt   SEVEN COLUMNS, one row per unit:
      <bundle> <arch> <model> <K> <depth> <arm> <layer>
      Cached units are NOT written to it and are NOT submitted, so a rerun
      after a failure queues only what is left and a warm matrix submits
      nothing at all.

  hpc/map.sbatch   ONE ARRAY TASK = ONE BUNDLE. It walks its bundle's rows and
      exports the row's axes per unit in a subshell (ECC_SWEEP=arch,
      ECC_SWEEP_ARCHS/ECC_CONST_ARCH, ECC_CONST_MODEL/ECC_SWEEP_MODELS,
      ECC_CONST_K/ECC_SWEEP_KS, ECC_WEIGHT_DEPTH_SCALE, ECC_RECON_ERT_ARM,
      ECC_LAYERS). THE SAME LIST IS IN THREE PLACES and each says so:
      run_all.sh's unit_env(), map.sbatch's loop and units._chip_cfg(). If
      they drift, the launcher skips units a job would re-solve.

  hpc/run_all.sh   THE ONLY LAUNCHER. Pins archs/ AND the task file per
      submission, sizes --array from the bundles, chains one dependent eval.
      --dry-run prints the bill and the bundling and submits nothing, and says
      in so many words that it cannot see the code a job runs.
      ECC_JOBS bundles round-robin (empty = one task per unit, today's
      behaviour exactly); a bundle is SERIAL, so ECC_MAP_TIME must cover it.

HOW A SWEEP DRAWS A PLACEMENT BAR
--------------------------------------------------------------------------
report/sweep.py was rewritten. The shape:

  ONE POINT OF THE X AXIS = ONE FULL PLACEMENT EVALUATION.
    _point_cfg()   cfg.with_(experiment="recon", sweep="fix",
                             const_arch=, const_model=, const_k=)
                   -- with_() re-resolves EVERYTHING, so pinning the three axes
                   moves code_k, code_t, every cache slug, and (for the
                   per-model ECC_LAYERS spelling) that model's OWN layer scope.
                   Which is why a model sweep can carry a scope per model now:
                   each point resolves its own. The result FILE each point
                   writes lands in the placement study's namespace, where it
                   belongs; the FIGURE, CSV and manifest are the sweep's.
    _evaluate_point() -> (point cfg, point session, placement out, Raw)
    _point_stack()    -> DataFrame, rows = categories, columns = the bars this
                   design could answer, built through `recon_view.bar_series`
                   -- THE PLACEMENT FIGURE'S OWN FOLD (external parity into the
                   DRAM band, then the `figure-draws-the-total` check), so a
                   bar means the same thing on both figures. Extracted from
                   `panel_for`'s `add()`; one routine, two callers.
    collect_points()  walks the axis and is THE ONLY PLACE the figure's data is
                   built -- run() draws what it returns and the metric-row
                   tests read the same call, so a test cannot pass against a
                   shape the figure never sees.

  A COLD POINT KEEPS ITS TWO REFERENCE BARS AND LOSES ITS RECONSTRUCTION ONES.
  A bch sweep is a sweep of the CODE: the reference arms exist at every code
  from ONE chip, while each boundary is a DIFFERENT chip per code and may not
  be mapped. Dropping the whole point would throw away two measured bars
  because a third is cold; billing the third from the reference plan would be
  Task 3 under a heading that says otherwise, which `no-boundary-mapped`
  refuses. So the refusal still fires inside the evaluation and sweep.py
  catches it BY GUARD ID:
      COLD_AT_THIS_POINT   ert-arm-cache-cold, ert-arm-shapes-differ,
                           arm-half-mapped, no-boundary-mapped
                           -> keep the two reference bars, drop the rest
      NOTHING_AT_THIS_POINT recon-nothing-collected, stacks-refused
                           -> drop the whole point
  Anything else PROPAGATES. A test asserts every id in both sets is a
  registered guard and that the two sets are disjoint.
  NOTE THE EXCEPTION TYPES: five of those guards raise SystemExit and the rest
  ConfigError, so sweep.py catches BOTH. Catching only ConfigError is how the
  first cut killed the whole figure on a point that should have lost one bar.

  A GROUP MAY BE MISSING A BAR, AND IT IS NEVER A ZERO.
  report/stacked.bar_value() returns None; draw_panel draws NOTHING there (no
  bar, no total label, no saving, no tag) and write_table leaves the cell
  EMPTY. A zero-height bar in a group that also holds real ones reads as a
  measured zero, and there is no such thing here. A bar that really IS zero
  still reads as 0.0 -- pinned by a test.
  draw_panel gained a LOOKUP, not a second routine (CLAUDE.md): it is still the
  only place a bar is drawn.

A BUG THE FREE-SETS SURFACED, AND WHY ONLY THIS DESIGN COULD FIND IT
--------------------------------------------------------------------------
`_constrain_mapspace()` APPENDED A SECOND `temporal:` KEY on
simple_weight_stationary -- duplicate-key YAML, which timeloopfe rejects, and a
constrained mapspace the mapper would never have seen.  Caught by
test_noc.py::test_injection_is_valid_yaml_on_every_arch_and_moves_the_fingerprint
the moment that design got a free-set.

  THE CAUSE: that design writes its constraints in FLOW style --
      temporal: {permutation: [P, Q, R, S]}
      temporal: {factors: [R=1, S=1, M=1, C=1]}
  -- and every other design writes them in BLOCK style.  Both of
  `_constrain_mapspace`'s regexes require a newline after `temporal:`, so
  neither matched, and the pins fell through to the `constraints:` branch,
  which CREATES a block.  The design has been in the study since the
  beginning; the bug was unreachable because it only declared a free-set today.

  THE FIX: a flow-style branch that merges into `{...}` -- into an existing
  `factors: [...]` where there is one, and adding one inside the braces where
  there is not.  It searches only AFTER `constraints:`, because a spatial
  container declares `spatial: {meshX: 16, meshY: 16}` as an ATTRIBUTE and
  pinning factors into the mesh would be rewriting the array.
  VERIFIED on all three designs: the pins land on the right levels, the free
  dimensions are the declared ones, and `_duplicate_keys` is None everywhere.
  eyeriss_like_wglb's 51 fingerprint rows are byte-identical after it, which is
  the proof it touched no design that writes block style.

P1  embedded < baseline in energy.  Baseline pays a dearer per-bit DRAM PRICE

P3  THE SHAPE ACROSS THE FOUR BOUNDARIES IS NOT MONOTONIC.  Going inward the

    So the net saving should RISE from R1 to R2 to R3 and then FALL BACK at
    R4a:

        R1  <  R2  <=  R3   >   R4a

    weight-stationary inner loop, where each resident weight is read many

    control, 3/5, 4/5, 2/5 -- the same shape.

P4  the percentage savings are SMALL in absolute terms -- low single digits of
    the total -- because at these two layers compute and activations dominate
    and the weight path is a minority of the total energy.  The ceiling line
    is what makes that arithmetic rather than a missing term.

P5  latency FALLS for every recon bar relative to baseline/embedded, and is
    roughly FLAT across R1-R4a.  The roofline binds on DRAM for these layers,
    all four boundaries cut off-chip weight bits by the same K/N, and none of

      R2   weight_glb storage       -> that level's UTILIZED instances, and a
                                       single global buffer has 1
      R3   inter_cluster_mesh, a NETWORK -> fanout x instances = one encoder
                                       per DESTINATION CLUSTER, so ~16
      R4   weights_spad storage, fills -> the UTILIZED PEs, up to 192
      R5a  weights_spad storage, reads -> the same ~192, and the event count
                                       becomes one rebuild per weight READ

    So predicted idle, at ~12 M cycles: R1/R2 ~0.16 uJ, R3 ~2.6 uJ, R4 and
    R5a ~31 uJ.  The 192-PE array is what makes R4 and R5a expensive here and
    it is a LARGER penalty than session 1 saw, where the same two inner
    boundaries had 16 engines on a 256-PE array.

Q5  THE SHAPE: R1 < R2, then the engine term bites.

        R1  <  R2  >  R3  >>  R4  >  R5a          (predicted)

    R2 is predicted the peak, and R4 and R5a are predicted NET PENALTIES.

Q6  THE ONE THE BRIEF ASKS FOR, AND IT IS A CROSSING CONDITION RATHER THAN A
    DIRECTION.  On simple_weight_stationary the peak was R2, not R3: R3 sat
    at the PE input with 16 cycle-weighted engines and paid 2.46 uJ of idle
    to buy 0.28 uJ of weight_noc saving, which contradicts Sec. 6.2's 4/5
    rating for R3.  DOES v2 REPRODUCE IT?

    Predicted: YES, R2 is still the peak -- but the margin is not the same
    and this is the least certain line here.  Two things differ, and they
    pull opposite ways:

      * v2's R3 does NOT sit at the PE input.  Its site is the inter-cluster
        MESH, so its engine count is one per cluster (~16) rather than one
        per PE.  Numerically that is the same order as session 1's 16, so
        the idle it pays is about the same ~2.6 uJ.
      * what R3 BUYS is bigger here.  It reduces TWO stages session 1's R3
        did not have separated -- the 288 B weight routers AND the
        hierarchical mesh -- and the mesh is the expensive hop on a 16 x 12
        array.  Session 1's R3 bought one weight_noc stage worth 0.28 uJ.

    So the separate weight_noc level does NOT change the engine count (the
    SITE does that, and R3's site is the mesh); it changes the SAVING.  The
    arithmetic test, to be checked against the result:

        R3 beats R2  <=>  (weight_noc + inter_cluster_mesh weight saving)
                          >  15 x idle_per_engine  ~=  2.5 uJ at 12 M cycles

    If v2's weight NoC term is larger than about 2.5 uJ over these two
    layers, R3 wins and session 1's inversion does NOT generalise.  If it is
    smaller, the inversion is a property of RULE 3's second denominator
    rather than of one design, which is the stronger result.

Q7  the savings are LOW SINGLE DIGITS of the total, as on every design at
    this scope: the ceiling line is what makes that arithmetic and not a
    missing term.

Q8  latency FALLS for every reconstruction bar against baseline/embedded and
    is FLAT across R1..R5a: all five cut the same off-chip weight bits by the
    same K/N, and none changes DRAM traffic relative to another.  This design
    declares `shared_bandwidth 0.12 items/cycle`, so the roofline has an
    off-chip limit to bind on.

Q9  EDP improves MORE than energy alone wherever energy improves, because
    energy and delay both fall; and on the bars that are energy PENALTIES the
    EDP penalty is SMALLER than the energy penalty, because the latency gain
    is still there.  (Session 1: R4a was +6.1% energy but only +1.9% EDP.)

Q10 area is ~flat: the DC engine at k=39 is 2,276.57 um2, tenths of a percent
