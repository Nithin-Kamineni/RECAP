  1. MAPPER IS OPTIMISING EDP, NOT ENERGY. This study reports energy, but the mapper is choosing mappings by a different objective. Under 'edp' an architecture with more MACs can buy latency by spending energy, so the wider array is systematically pushed to a costlier mapping. Set ECC_OPT_METRIC=energy.

      the same node and datawidth. If it differs by ~2x, one design

NEXT STEPS
==============================================================================
  The mapper is minimising edp, not energy. Set
  ECC_OPT_METRIC=energy before comparing architectures by energy.

  Equalise the storage datawidth -- one variable, and the cheapest fix:
     ECC_FORCE_DATAWIDTH=8 bash run.sh
  That is a no-op on any design already declared at the weight width, so
  those architectures keep their existing mapper cache and only the
  mis-declared ones are re-mapped.
  The treated results get their own raw-cache subtree, so nothing
  already collected is overwritten or mixed in.

  ECC_FORCE_TECHNOLOGY changes globals.yaml, which costs DRAM for EVERY
  design at once, so it invalidates every cache. Only worth it if you
  specifically want DRAM costed at the same node as the accelerators;
  all five arch containers already declare 45nm.
